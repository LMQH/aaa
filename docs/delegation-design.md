# 委派机制：需求设计

## 目标与范围

主 Agent 可以把独立任务交给其他执行对象，而不把子任务的对话过程塞进主会话。aaa 以内置工具 `delegate_task` 复现 Hermes 的同进程线程委派形态，执行复用 Agno 原生机制；首版同时支持 Agent、Team、Workflow 三种委派对象。子进程是后续可选后端，本版不实现，也不承诺进程级隔离或强制终止。

## 三种委派对象

| 对象 | 用途 | 执行边界 |
|---|---|---|
| Agent | 独立执行一个子任务 | 用原生 `Agent.run()` 运行独立子 Agent |
| Team | 多个成员协作完成一个子任务 | 用原生 `Team.run()` 执行；成员协作由 Agno 决定，不由主会话或工具重写 |
| Workflow | 按固定步骤执行一个子任务 | 用原生 `Workflow.run()` 执行；步骤由 Agno 驱动，不由主会话逐步调度 |

## 定义、保存与复用

- Agent、Team、Workflow 都可现场定义、直接委派及独立保存。定义默认只在创建会话可见；模型仅在有复用价值时主动提议，用户明确要求保存时直接发起请求。用户确认后保存同一份定义及为它现场创建的私有依赖；公共依赖保留引用，运行时重新解析并检查权限。运行进度、线程和当次审批不随定义保存。
- **保存与执行分别授权。** 模型可先生成 Workflow、技能或插件的草案；最终落盘须经用户确认。批准保存不授予未来运行权限，也不替代具体动作的审批。
- **只能组合已有的 Agno 执行对象。** 模型可以定义步骤、依赖、分支与并行，但每个执行步骤只能引用宿主可解析且调用方有权使用的 Agent、Team 或 Workflow。分支与并行是 Agno 的编排结构，不是第四种执行能力。定义不能嵌入任意代码、注册新执行能力或扩大权限。
- **创建、注册、执行分开。** `register_delegation` 接收一份 `{entry, definitions}`，校验后临时注册整组；`list_delegations` 发现可见入口以及可用模型与工具；`delegate_task` 接收有序 `{ref, input}` 列表。Agno 负责步骤推进，工具不接受未注册的现场定义。

## 调用与执行边界

1. 主会话始终由原生 `Agent.run()` 驱动，暂停后的续跑仍由 Agno 管理。主 Agent 决定何时调用 `delegate_task`，选择委派对象并显式传入任务及必要上下文。
2. `delegate_task` 由宿主装配，不是插件，也不是模型动态创建的工具。一次调用可提交多个任务；工具在本次调用内部用有并发上限的线程池执行，因为当前 Agno 同步路径会串行处理工具调用。
3. 每个顶层委派任务使用独立的执行对象与会话身份，不继承主会话历史；Team 成员之间或 Workflow 步骤之间的信息传递由各自的 Agno 执行体管理。子执行对象的工具权限不得高于主会话，同进程不是 OS 沙箱。
4. 首版只做同步委派，不转发交互审批。任何子执行对象遇到需要用户确认的动作都不执行，并将拒绝原因返回主 Agent；主 Agent 若仍需执行该动作，必须走现有用户审批。
5. 同步调用汇总各任务的结果后返回主 Agent。结果应能关联原任务、区分成功与失败等状态，并携带可用的结果或失败原因；一个任务失败不能抹掉同批其他任务的结果。线程执行没有进程退出码。

## 实现约定

- Team 支持 `coordinate`、`route`、`broadcast`、`tasks`；同步 `broadcast` 不承诺成员并发。现场定义的成员角色与指令由模型决定；模型与工具只能取宿主允许的选项。子工具不包含委派、注册或保存入口。
- Agno 3.1.12 的 `tasks` 在 `execute_task` 后未自动刷新已阻塞的依赖。领队确认前置任务确实成功后，经 Agno 原生 `update_task_status` 更新状态，再执行依赖项；aaa 不改原生任务清单或调度器。
- Workflow 用 Agno `Step`、`Parallel` 和 `Condition` 表达执行、并行和条件分支。条件只比较前序输出与字面字符串；循环引用在注册前拒绝。
- `save_delegation` 以用户审阅的完整定义为确认对象；不用审批签名缓存，不自动覆盖。同一份定义可保存于 `~/.aaa/data/delegations/`，私有依赖不在其他会话的发现列表中单独出现。
- 主会话取消后不再启动排队项，已启动项交给对应 Agno `cancel_run()`。单项超时只请求取消；原生执行真正退出前仍占用并发名额。委派结果回到主会话，子会话不加入会话索引或独立账本归因。

## 验收标准

- 在同一个主 Agent 会话中，能分别委派一个 Agent 任务、一个实际调用成员的 Team 任务和一个实际运行步骤的 Workflow 任务；每次结果都回到原主会话，无需切换会话执行体。
- 一次调用提交多个独立任务时，执行时间有重叠且不超出并发上限；部分任务失败时，其余结果仍可用。
- 子任务不会自动收到主会话历史，也不能取得主会话未获授权的能力；子任务的内部过程不会被写成主会话历史。
- 未确认保存时不写入持久存储；确认后，新会话可复用原定义及其私有依赖。例如仅为该 Workflow 创建的 Team 不需要重新定义。
- 子任务触发需用户确认的动作时，该动作不执行、不弹出子任务审批，主 Agent 收到拒绝原因。
- 取消、超时和执行完成分别报告；不把停止等待误报为线程退出。

## 概念验证（POC）

离线 POC 已验证：不改主循环即可从线程调用原生 Agent、Team 和嵌套 Workflow；取消须由外层委派工具显式转发给子执行对象。

1. 用同一最小流程引用一个 Agent、一个实际调用成员的 Team、一个至少执行一步的嵌套 Workflow。由主 Agent 调用 `delegate_task`，用步骤输出与原生执行记录确认三类对象确实运行、结果回到原主会话，不以构造成功或返回一句成功作为通过。
2. 先临时注册并运行；验证新会话看不到未保存的定义。保存原定义后，在新会话发现并重新运行，核对两次使用的是同一份流程定义。
3. 提交引用未知对象或非上述三类执行能力的定义，确认注册失败且没有启动步骤。

POC 使用隔离环境与临时存储；不要求接入正式 CLI、配置或账本。
