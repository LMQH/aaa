# 目标工程：如何为 Agent 设计目标（Goal Engineering）

**结论**：目标型 Agent 的范围设计原则是——把目标划在「人最容易给出高质量反馈」的边界上。Agent 出错的主因是缺上下文，而最难补的上下文是没写下来的、只在人脑中的专家经验，只能靠人工反馈传递；因此审阅 UX 与反馈收集的易用性是核心投入点，而非附属功能。置信度：高（一手原文，含 Actively AI 实证案例；结论为作者实践归纳）。

## 1. 为什么反馈是设计目标的核心约束

Agent 能承担的范围已从文本生成 → 工具调用与决策 → 执行完整任务，未来是承担开放式目标并自主推进（如 [Hone](https://x.com/hone/status/2108218574926176490?s=20)，其关键设置之一就是给 Agent 定义可优化的指标）。方向指错 = 大量 token 浪费。

Agent 出错的很大原因是缺正确上下文。上下文分两类：

- 文档、API 等已写下的信息——相对容易补给；
- **从未写下来、只在专家脑中的经验**——只能通过人工反馈传递，最难补。

随着 Agent 从可验证任务扩展到与人类协作的主观性工作（如优化广告文案：品牌调性、多大尺度算出格，这些偏好无法预先写全），无法高效获取反馈的 Agent 会迅速变得无用。

**推论**：设计 Agent 范围时，让「在其工作范围内给出大量高质量反馈」尽可能容易；同时投入直观愉悦的**审阅 UX**——Agent 表现的瓶颈往往是从反馈中学习，反馈收集的易用性与质量就是优化目标。

## 2. 案例：Actively AI 的两次迭代

Actively AI 为销售团队构建目标型 Agent。

**v1：按账户（account）划分**。每个潜在客户一个 Agent，目标是推进该账户成交，产出动作供销售审批。看似合理：目标有界、结果明确，账户信息是最重要的上下文。实际发现问题：

- 推进单个账户的多种工作分散在不同时间，单账户 Agent 待审事项少，销售频繁在多个 Agent 间切换上下文；
- 「怎么做销售」的知识（怎么外呼、怎么回复、怎么谋略、多强势、怎么穿越大组织）跨 Agent 通用，但 UX 上很难把一个账户学到的经验共享给其他账户。

**v2：按动作（motion）划分**（基于 [Deep Agents](https://github.com/langchain-ai/deepagents) 构建）。motion 是一类待完成的工作，如「外呼」「早期商机推进」。要点：

- 同一 motion 是一批相似任务，销售可以集中批量审阅，反馈成本大幅降低；
- 对 motion 中一个任务的反馈，自然迁移到该 motion 的其他任务——知识与反馈天然对齐到 Agent 的范围；
- 账户信息并未被抛弃：它相对客观且多已写下来，由后台的上下文收集 Agent 按需汇总；推进漏斗的实际工作交给跨账户的 motion。

核心经验：**将反馈的范围与易用性对齐到 Agent 自身的范围**，Agent 才能学得快、变得强。

## 3. 展望

未来 Agent 拿到目标即自主优化。人工审阅耗时但极有价值——那是教会 Agent 领域知识、适配你的业务的唯一途径。要把人脑中的隐性知识提取成易传递的形式，就要**把 Agent 的目标对齐到人最容易审阅的形状**。
