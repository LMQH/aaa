# Agno 与 Pi Core 对比调研：自研 Harness 的两条起点

日期：2026-11-11
范围：Agno 3.1.12（本机源码 + 官方文档）、Pi 分层结构（`Pi-分层结构详解.md` 及源码快照）
用途：为“从 SDK 搓出一个可用 coding agent”的选型提供判断依据
关联：`Harness最小实现公式模型与闭环实现准则.md`（五项公式）、`模型上下文治理方案.md`（Context 治理）、`Agno-SDK原生覆盖能力调研.md`（Agno 逐项证据）

## 一、结论摘要

**两者总工作量相近，但工作量的性质不同。** 同样的六件事，Agno 多数给配置、少数给接缝；Pi Core 多数给接缝、少数给实现。差别不在“做多少”，而在“改得动多少”。

| 判断 | 结论 |
|---|---|
| 快速做出可信单机 coding agent | Agno 明显更快，约省一半工作量 |
| 做长会话、多用户、成本可控的系统 | 工作量趋同，Agno 的工作会转化为“改框架” |
| 做 Doc 1 + Doc 2 描述的治理形态 | 两者都只能当“端 + 循环”，治理必须自建 |

## 二、三者定位

| 对象 | 定位 | 优化目标 | 代价 |
|---|---|---|---|
| **Agno**（同类：LangGraph） | 应用搭建框架 | 广度优先：工具、记忆、知识、团队、工作流、运行时、评估、调度一次给齐 | 装配与循环收在内部，不可介入 |
| **Pi** | 分层运行时 | 深度优先：模型层、Agent core、编码应用层，主干做薄且留缝 | 广度全靠扩展、技能、自建 |
| **Doc 1 + Doc 2** | 可治理 Harness | 在五项职责之上，要求“状态 → 视窗”的治理模型与统一边界策略 | 无现成 SDK 以它为目标 |

一句话：**前两者都不以“治理”为目标，所以它们缺的不是同一件东西。**

## 三、五项公式对照

| 组件 | Agno | Pi | 差异性质 |
|---|---|---|---|
| **Provider** | 54 家供应商统一适配；请求级与整轮重试；回退模型；token 与成本计量（含缓存字段） | 独立 pi-ai：多供应商、鉴权、模型目录、流式适配 | 差异小，都能直接沿用 |
| **Tools** | 152 个工具模块；函数 / Toolkit / MCP / Context Provider / 内置文件系统五种来源；并行调用；超大结果卸载为可回读指针 | core 只定义工具语义与调度，不提供编码工具；coding-agent 层内置 read/bash/edit/write/grep/find/ls，扩展可注册工具 | 差异大：广度 vs 薄 |
| **AgentLoop** | 循环完整但封闭：仅 run 前后与工具前后钩子；有 `tool_call_limit`，无 Agent 级轮次上限 | 循环公开：可注入模型流、消息转换、上下文变换、工具前后钩子、回合停止判断、下一回合准备 | 差异大：可配置 vs 可介入 |
| **Context** | 装配菜单齐全：历史窗口、会话摘要、压缩（阈值 + 保留尾 + 摘要预算 + 归档）、工具结果卸载、记忆、知识、依赖、状态、Context Provider、Skills；治理只有压缩与卸载两条机制，无驻留预算与阶梯；会话为 runs + summary + 压缩记录 | 有 session、compaction、上下文变换等原语；无治理策略；会话为可恢复的条目记录 | Agno 有内容没有控制；Pi 有控制点没有内容策略 |
| **Boundary** | Guardrails 输入校验、HITL 审批、调用次数与重试配额、沙箱执行契约（后端 docker/agentcore，归属 AgentOS）；无统一策略源、无权限驱动可见性 | 分层文档未涉及权限、沙箱、配额 | 都不完整；Agno 略强 |

## 四、自研 coding agent 的六件事

| 能力 | Agno | Pi Core | 谁省 |
|---|---|---|---|
| 模型接入 | 配置 | 接 pi-ai，配置 | 相当 |
| 编码工具 | 现成包：workspace、shell、fs、coding | core 无，需自写或改用 coding-agent 层 | Agno |
| 会话持久化 | 15 种数据库开箱即用 | 有 session 原语，存储自接 | Agno |
| 上下文压缩 | 配置面：折叠阈值、保留尾轮数与体积上限、摘要预算、原文归档加检索工具、溢出重折；无驻留预算与阶梯 | compaction 原语：摘要、保留尾部、可介入 | 两者都能折叠；Agno 缺成本治理，Pi 缺策略 |
| 权限与沙箱 | HITL 标记、Guardrails 现成，沙箱外挂 | 全部自建 | Agno 略省 |
| 对外接口 | AgentOS 直接给 REST/SSE、调度、RBAC | 自写 | Agno |

清单层面确实“差不多”；差别在每一项是配置还是实现。

## 五、分水岭：“可用”的两种定义

**定义 A：可信单机、单人用、任务短。**
Agno 明显更快——工具、持久化、接口全部现成，Pi Core 反而要自己接工具、存储与入口。此场景下两者差距可达一倍。

**定义 B：长会话、多用户、成本可控、输入不可信。**
工作量趋同，但 Agno 的治理工作会从“配置”变成“改框架”：装配在 Agent 内部完成，没有请求前接缝，会话模型（runs + summary + 压缩记录）不配合条目流式视窗重建，治理只能塞进 Model 子类或 fork。Pi 的工作仍是“写策略”，因为接缝本身就是公共 API。

## 六、隐性成本：改得动与改不动

- **Agno 的强项就是天花板**：能配置的都已配置好；配不到的地方要和私有实现竞争，升级时治理补丁要重做。
- **Pi Core 的弱项就是自由**：工具、存储、接口都要写，但每行代码在自己地基上，升级只跟公共契约打交道。
- **锁定程度**：用了 Agno 的 Team/Workflow/AgentOS 后退出成本高；Pi 是纯库，退出容易。

结论：**前三个月差不多，后六个月开始分叉。**

## 七、选型决策

| 场景 | 选择 |
|---|---|
| 尽快产品化，需要 API、RBAC、调度、评估 | Agno |
| 自研 Harness，长会话成本敏感，要求循环与上下文可介入 | Pi Core（或直接用 Pi coding-agent） |
| 目标就是 Doc 1 + Doc 2 的形态 | 任一 SDK 只当“端 + 循环”，治理层自建 |

## 八、各自要补的清单

**基于 Agno 落地需补**

1. 每次模型请求前的接缝（预检、提交、预算）。
2. 条目流与视窗分离的数据模型（现有 runs + summary 不满足）。
3. Agent 级轮次上限与明确终止原因。
4. 沙箱策略（执行契约已有，隔离范围与授权没有）。
5. 统一权限策略源（授权、可见性、配额分散在五处）。
6. 模型窗口与单价元数据。

**基于 Pi Core 落地需补**

1. 编码工具集（或改用 coding-agent 层）。
2. 持久化落地（把 session 原语接到具体存储）。
3. 权限、沙箱、配额。
4. 对外接口（CLI、RPC 或 HTTP）。
5. 上下文治理策略（压缩原语之上没有双旋钮、阶梯淘汰、成本归因）。
6. 评估、可观测、多 Agent（若需要）。

## 九、证据与限制

- Agno 结论绑定本机 `agno 3.1.12`，逐项出处见 `Agno-SDK原生覆盖能力调研.md`；文档站可能领先安装版本。
- Pi 结论基于 2026-09-11 的分层文档与源码快照，本轮未重新核对最新上游；“文档未涉及”不等于“实现不存在”，尤其 Boundary 部分。
- 工作量判断为结构性判断，非工时估算；实际差异随团队对框架内部的熟悉程度变化。
