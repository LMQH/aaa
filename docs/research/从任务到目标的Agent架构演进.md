# 从任务到目标：面向持续结果的 Agent 架构

**结论**：Agent 能力增强后，人机协作正从「给 Agent 派任务（Task）」转向「给 Agent 托付目标（Goal）」——不是写更长的提示词，而是把「做什么工作、何时去做」的决策权委托出去，人的角色转为定方向、划边界、审进展。这一转变改写了 Agent 的六个工程侧面，每项都对应明确的落地要求。置信度：高（一手原文，观点性文章，结论为作者判断而非实证）。

- **原文**：[From tasks to goals — Harrison Chase (LangChain CEO)](https://www.langchain.com/blog/from-tasks-to-goals)，2026-11-16
- **姊妹篇**：[Goal Engineering: How to Design Goals](./从任务到目标的Goal设计方法.md)（2026-11-14，讲如何设计便于反馈的目标）

## 1. 范式跃迁：从「有界动作」到「持续结果」

底层包含两层实质变化：

- 从指定**具体动作** → 指定**预期结果**
- 从**有界指派** → **持续职责**

| 任务模式（动作/有界） | 目标模式（结果/持续） |
|---|---|
| 写好这封邮件 | 降低沟通协调负担，同时确保关键承诺按期推进 |
| 起草这篇博客 | 持续维护并运营一个博客 |
| 修复这个 Bug | 让这款产品取得成功 |

任务型 Agent 是单次闭环（指定任务 → 执行 → 对话澄清 → 完成 即停止）；目标型 Agent 是持续循环（设定目标 → 自主发散挑选任务 → 受控执行 → 靠触发器唤醒/主动暂停 → 指标与人工反馈沉淀为跨轮次记忆 → 再触发）。

## 2. 六项系统性工程变化

### 2.1 Agent 自主拆解、挑选并维护任务列表

用户只给目标，Agent 自己将目标拆解为任务、执行一部分、再更新任务清单。要求 Agent 在发散任务时有一定创造性与多样性（反复提同样的任务不可接受）。

**落地要求**：可视化的任务清单（to-do list）+ 提示策略驱动其发散。

### 2.2 工具调用不可预知

派任务时大致知道会用哪些工具（发邮件 → Gmail + 日历）；给目标时无法预知会用到邮件、短信、搜索、浏览器还是其他工具。

**落地要求**：更细粒度的工具权限控制（允许/禁止调用哪些工具）。

### 2.3 后台提问通道（收件箱）

任务模式下 Agent 天然在对话环内，缺信息可直接追问；目标模式下 Agent 常在后台运行，需要异步向人提问的机制。

**落地要求**：后台 Agent 的提问通道（Slack 或专用 UI）。

### 2.4 进展反馈机制

Agent 需要知道自己朝目标的进展：可查指标（易自动跟踪，但不宜盲目优化单一指标），也可取人工反馈（表达主观偏好）。两者可并存。

**落地要求**：目标设计对齐反馈方式（见姊妹篇 Goal Engineering），并建立反馈收集机制。

### 2.5 触发器与停止规则

任务跑完即止；目标需要 Agent 在后台间歇工作。唤醒方式：定时心跳（每 X 分钟）、周期 cron、一次性 cron（提醒）、监听事件流。同时必须有停止/暂停/忽略触发的规则——每 30 分钟被心跳唤醒后重复问同一个问题是糟糕体验。「持续职责」不等于总要做点什么，**有时什么都不做才是正确动作**。

**落地要求**：cron 与事件触发器 + 提示 Agent 自行判断何时行动。

### 2.6 记忆让反馈复利

任务模式下用户每次提供上下文即可，记忆需求不大；持续职责下上下文负担转移给 Agent，它必须跨轮次携带决策与反馈。例：否掉一个博客选题应影响今后的选题，而不只是当前这一稿。

**落地要求**：跨运行保留并使用相关决策与反馈。

## 3. 核心论断

给 Agent 一个目标 ≠ 给它一段更长的提示词，而是委托「做什么、何时做」的决策权。人的角色从逐项派发任务，转向设定方向、划定边界、审阅进展。
